# Sprint 1 Blueprint — Deployment Audit & Environment Hardening

Readr v3.0

**Objective:** Audit the current Vercel + Render + Neon deployment and remove environment and configuration fragility. This sprint establishes a clear production baseline for the rest of v3.0 hardening work. :contentReference[oaicite:0]{index=0}

---

# Sprint 1 Goal

- Production deployment paths are clearly understood
- Environment variables are standardized
- Localhost assumptions are removed
- Frontend, backend, and database connectivity is validated end-to-end

---

# Scope

## Deployment Audit

- Document the current Vercel frontend deployment
- Document the current Render backend deployment
- Document Neon’s role in the production architecture
- Verify request flow between frontend, backend, and database

---

## Environment Review

- Audit all environment variables used by client and server
- Standardize `.env.example` files
- Confirm production and local variable naming is consistent
- Remove stale, duplicate, or unused environment keys

---

## Production Config Hardening

- Remove any remaining localhost fallbacks in production paths
- Verify frontend API base URL resolution
- Verify backend CORS configuration against the deployed frontend origin
- Verify database connection handling in production

---

# Execution Checklist

## 1) Audit deployed Vercel + Render + Neon architecture

- [ ] Confirm the production frontend host and URL
- [ ] Confirm the production backend host and URL
- [ ] Confirm the backend health endpoint
- [ ] Confirm Neon is the active production database provider
- [ ] Map the production request flow:
  - browser -> Vercel frontend -> Render backend -> Neon database
- [ ] Identify any legacy or unused deployment assumptions

## 2) Verify production connectivity and Neon reliability baseline

- [ ] Load the deployed frontend successfully
- [ ] Inspect the browser Network tab for live API requests
- [ ] Confirm no production requests target localhost
- [ ] Hit the backend health endpoint directly
- [ ] Test at least one database-backed production route
- [ ] Note any cold starts, flaky startup, timeout behavior, or deployment pain points

## 3) Standardize environment variables across client, server, and deployment

### Client audit

- [ ] Search for `import.meta.env`
- [ ] Search for `VITE_`
- [ ] Search for `localhost`
- [ ] Search for hard-coded API URLs
- [ ] List all client environment variables actually used
- [ ] Compare actual usage against `client/.env.example`
- [ ] Add missing keys
- [ ] Remove stale keys
- [ ] Normalize names, examples, and comments where needed

### Server audit

- [ ] Search for `process.env`
- [ ] Search for `DATABASE_URL`
- [ ] Search for `PORT`
- [ ] Search for auth-related environment keys
- [ ] Search for `CORS` and `ORIGIN`
- [ ] Search for `localhost`
- [ ] List all server environment variables actually used
- [ ] Compare actual usage against `server/.env.example`
- [ ] Add missing keys
- [ ] Remove stale keys
- [ ] Normalize names, examples, and comments where needed

## 4) Remove localhost assumptions from production paths

### Frontend

- [ ] Audit API base URL resolution
- [ ] Remove unsafe localhost fallbacks from production behavior
- [ ] Confirm production resolves the deployed backend intentionally
- [ ] Confirm local development still works intentionally

### Backend

- [ ] Audit config for localhost assumptions
- [ ] Verify backend CORS configuration against the deployed frontend origin
- [ ] Confirm production-safe origin handling
- [ ] Verify database connection handling is production-safe

## 5) Re-validate production after cleanup

- [ ] Reload the deployed frontend after config cleanup
- [ ] Re-check the browser Network tab for API targets
- [ ] Re-check the backend health endpoint
- [ ] Re-test a database-backed route
- [ ] Confirm no production path depends on localhost
- [ ] Confirm no CORS failures remain
- [ ] Confirm frontend, backend, and database connectivity remains stable end-to-end

---

# Acceptance Criteria

- Production architecture is clearly documented
- Frontend communicates correctly with backend in production
- Backend communicates correctly with Neon in production
- No production behavior depends on localhost
- `.env.example` files are updated and accurate

---

# Deliverables

- updated `.env.example` files
- deployment notes for Vercel, Render, and Neon
- cleaned environment variable usage
- verified production connectivity flow

---

# Notes

- Sprint 1 is about removing ambiguity and hidden fragility.
- No major hosting changes should happen in this sprint.
- This sprint creates the baseline for all later v3.0 hardening work. :contentReference[oaicite:1]{index=1}

---

### Deployment environment baseline

- Render is the active backend runtime environment and holds the backend-required variables.
- Vercel provides the frontend build-time API base URL through `VITE_API_BASE_URL`.
- Vercel currently also contains several Neon-generated database variables that may be stale for the deployed frontend and should be reviewed for removal.
- Local client environment configuration was found to be out of sync with actual client code expectations.
