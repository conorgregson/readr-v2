# Sprint 2 Blueprint — Docker & Local Environment Standardization

Readr v3.0

**Objective:** Standardize local development with Docker so the app is easier to run, test, and maintain across environments.

---

## Sprint 2 Goal

- Local backend runs in a containerized workflow
- Supporting local services are easier to orchestrate
- Local environment setup becomes more predictable
- Docker improves consistency without replacing the current hosted stack

---

## Scope

### Containerization

- Add Dockerfile for backend
- Keep frontend Docker optional unless it proves necessary
- Add `.dockerignore` files
- Validate production-style backend container startup

---

### Local Orchestration

- Add `docker-compose.yml` for local development
- Support local API + database workflows through Compose
- Ensure environment variables work correctly inside containerized setup
- Document how Docker integrates with existing dev flow

---

### Developer Experience

- Minimize setup friction for local development
- Ensure clean startup/shutdown workflow
- Validate that Docker-based local flow does not break existing scripts
- Keep non-Docker local workflow optional if desired

---

## Execution Plan

### Phase 1 — Backend Container Foundation

- Create backend Dockerfile
- Add root `.dockerignore` for clean build context
- Ensure the backend can install dependencies and start correctly inside a container
- Support the repo’s actual workspace, shared types, and TypeScript config structure

### Phase 2 — Local Database Orchestration

- Add a root-level `docker-compose.yml`
- Add a local Postgres service for development
- Add a backend service wired to the local Postgres container
- Add a persistent Docker volume for database state

### Phase 3 — Environment Standardization

- Verify Docker-safe local environment variables
- Keep local Docker values separate from hosted production values
- Confirm `DATABASE_URL`, backend port, and local frontend origin work correctly in the containerized setup
- Ensure shared config files required by the server are available inside the container

### Phase 4 — Verification Pass

- Build backend container successfully
- Start services with `docker compose up`
- Confirm backend health route responds locally
- Confirm backend can connect to containerized Postgres
- Confirm Prisma generation works in the Dockerized workflow
- Confirm existing non-Docker development can remain optional

### Phase 5 — Documentation

- Add README section for Docker local setup
- Document startup, shutdown, rebuild, and reset commands
- Explain that Docker is for local consistency and does not replace the hosted Vercel + Render + Neon deployment model

---

## Acceptance Criteria

- Backend container builds successfully
- Docker Compose starts the required local services
- Local development can run from a documented container workflow
- Environment configuration works inside Dockerized setup
- Existing development workflow is either preserved or clearly replaced

---

## Deliverables

- backend `Dockerfile`
- root `.dockerignore`
- `docker-compose.yml`
- Docker-aware environment handling for local development
- README local Docker setup section

---

## Verification Pass

### Verified

- `docker compose up` successfully started the local Postgres container and backend container
- Postgres started successfully from the Dockerized local workflow
- Prisma client generated successfully inside the backend container
- backend started successfully with `ts-node-dev`
- backend reported a successful startup message on port `4000`
- local `/health` endpoint responded successfully, confirming the Dockerized backend is reachable and healthy

### Notes from Verification

- Initial Sprint 2 work required resolving Docker Desktop / WSL instability before the application workflow could be validated
- Container setup also required aligning Docker with the repo’s actual TypeScript and workspace structure
- Once corrected, the backend + database Docker workflow ran successfully end to end

---

## Notes

- Docker is included because it solves a real consistency problem
- This sprint should improve setup clarity, not add unnecessary complexity
- Frontend containerization remains optional and was not required to validate the local backend workflow
- Kubernetes remains out of scope

---

## Sprint 2 Status

**Current status: Core Sprint 2 backend Docker workflow verified**
