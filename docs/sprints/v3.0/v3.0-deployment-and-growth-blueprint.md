# Version 3.0 — Deployment & Growth

**Focus:** Harden Readr’s existing deployed stack for reliability, consistency, and production maturity.

This version is split into five focused sprints so deployment hardening, local workflow improvements, observability, and documentation can be completed in a controlled way without turning v3.0 into an unnecessary infrastructure migration.

---

## v3.0 Pre-Sprint Checklist

Use this before Sprint 1 to make sure the deployment-hardening work starts from a clear baseline.

### Deployment Inventory

- Confirm current frontend host, backend host, and database provider
- Confirm production frontend URL, backend URL, and health endpoint
- Confirm where environment variables are currently stored and managed
- Confirm which services are actively used versus legacy/unused setup

### Environment Baseline

- List all client environment variables currently in use
- List all server environment variables currently in use
- Identify missing, duplicated, stale, or inconsistently named variables
- Confirm production values differ correctly from local development values

### Deployment Health Baseline

- Verify deployed frontend loads successfully
- Verify deployed backend health route responds correctly
- Verify frontend can communicate with backend in production
- Verify backend can communicate with Neon successfully
- Note any flaky behavior, cold starts, or recurring deployment issues

### Risk Review

- Identify any remaining localhost assumptions
- Identify any hard-coded URLs or environment fallbacks
- Identify any manual deployment steps that are easy to forget
- Identify any current pain points in debugging production issues

### Docker Readiness

- Confirm what should be containerized in local development
- Decide whether Docker support is backend-only or includes frontend
- Confirm whether local database workflow should stay as-is or be included in Compose
- Note any scripts or workflows that may need adjustment once Docker is added

### CI/CD Baseline

- Confirm current CI checks already in place
- Identify gaps in deploy-readiness validation
- Confirm whether release steps are currently documented or ad hoc
- Note any recurring issues during pushes, builds, or production verification

### Documentation Baseline

- Confirm whether README accurately reflects the deployed architecture
- Confirm whether local setup instructions still match reality
- Identify missing documentation for environment setup, deployment flow, or recovery steps

### Success Criteria for v3.0

- Define what “deployment hardening complete” means for this release
- Define what must be true before v3.0 can be considered release-ready
- Confirm that v3.0 is improving reliability and maintainability rather than changing infrastructure for its own sake

### Notes

- This checklist is not a formal sprint.
- It exists to reduce ambiguity before Sprint 1 begins.
- Any unresolved items here should feed directly into Sprint 1 scope rather than becoming separate roadmap work.

# Sprint 1 Blueprint — Deployment Audit & Environment Hardening

Readr v3.0

**Objective:** Audit the current Vercel + Render + Neon deployment and remove environment/configuration fragility.

---

## Sprint 1 Goal

- Production deployment paths are clearly understood
- Environment variables are standardized
- Localhost assumptions are removed
- Frontend/backend/database connectivity is validated end-to-end

---

## Scope

### Deployment Audit

- Document current Vercel frontend deployment
- Document current Render backend deployment
- Document Neon database role in the architecture
- Verify domain and API flow between all services

---

### Environment Review

- Audit all environment variables used by client and server
- Standardize `.env.example` files
- Confirm production vs local variable naming is consistent
- Remove stale or unused environment keys

---

### Production Config Hardening

- Remove any remaining localhost fallbacks in production paths
- Verify frontend API base URL resolution
- Verify backend CORS configuration against deployed frontend origin
- Verify database connection handling in production

---

## Acceptance Criteria

- Production architecture is clearly documented
- Frontend communicates correctly with backend in production
- Backend communicates correctly with Neon in production
- No production behavior depends on localhost
- `.env.example` files are updated and accurate

---

## Deliverables

- updated `.env.example` files
- deployment notes for Vercel, Render, and Neon
- cleaned environment variable usage
- verified production connectivity flow

---

## Notes

- Sprint 1 is about removing ambiguity and hidden fragility.
- No major hosting changes should happen here.
- This sprint creates the baseline for all later v3.0 hardening work.

---

# Sprint 2 Blueprint — Docker & Local Environment Standardization

Readr v3.0

**Objective:** Standardize local development with Docker so the app is easier to run, test, and maintain across environments.

---

## Sprint 2 Goal

- Local backend runs in a containerized workflow
- Supporting local services are easier to orchestrate
- Local environment setup becomes more predictable
- Docker improves consistency without replacing the current hosted stack

---

## Scope

### Containerization

- Add Dockerfile for backend
- Add optional Dockerfile for frontend if useful
- Add `.dockerignore` files
- Validate production-style backend container startup

---

### Local Orchestration

- Add `docker-compose.yml` for local development
- Support local API + database workflows through Compose
- Ensure environment variables work correctly inside containerized setup
- Document how Docker integrates with existing dev flow

---

### Developer Experience

- Minimize setup friction for local development
- Ensure clean startup/shutdown workflow
- Validate that Docker-based local flow does not break existing scripts
- Keep non-Docker local workflow optional if desired

---

## Acceptance Criteria

- Backend container builds successfully
- Docker Compose starts the required local services
- Local development can run from a documented container workflow
- Environment configuration works inside Dockerized setup
- Existing development workflow is either preserved or clearly replaced

---

## Deliverables

- backend `Dockerfile`
- optional frontend `Dockerfile`
- `.dockerignore` files
- `docker-compose.yml`
- README local Docker setup section

---

## Notes

- Docker is included because it solves a real consistency problem.
- This sprint should improve setup clarity, not add unnecessary complexity.
- Kubernetes remains out of scope.

# Sprint 3 Blueprint — Reliability, Health Checks & Runtime Visibility

Readr v3.0

**Objective:** Improve confidence in the deployed application through better health signaling, error visibility, and runtime diagnostics.

---

## Sprint 3 Goal

- Deployment health is easier to verify
- Runtime failures are easier to diagnose
- Production behavior is more observable
- Core hosting/security assumptions are revalidated

---

## Scope

### Health & Readiness

- Review and strengthen health check coverage
- Define backend readiness expectations
- Verify deployment startup behavior on Render
- Confirm Neon connection reliability during startup/runtime

---

### Logging & Diagnostics

- Improve structured logging baseline
- Ensure important operational errors are surfaced clearly
- Reduce noisy or unhelpful logs
- Make failures easier to distinguish across client, server, and database boundaries

---

### Configuration & Safety Review

- Re-check CORS behavior
- Review security headers and deployment-safe config
- Verify error responses are useful but not overly noisy
- Validate production-safe failure handling for unavailable backend/database cases

---

## Acceptance Criteria

- Health check behavior is stable and meaningful
- Backend startup expectations are documented
- Production failures are easier to diagnose
- Logging is more consistent and useful
- Deployment-safe config is reviewed and verified

---

## Deliverables

- improved health/readiness flow
- stronger logging baseline
- runtime diagnostics notes
- updated deployment safety/config review notes

---

## Notes

- Sprint 3 is about operational confidence, not feature work.
- Observability should stay lightweight and appropriate for the project’s scale.
- The goal is better failure visibility, not enterprise monitoring complexity.

# Sprint 4 Blueprint — CI/CD & Release Confidence

Readr v3.0

**Objective:** Improve release safety by validating deployment readiness earlier and making pushes to production more predictable.

---

## Sprint 4 Goal

- CI validates deploy readiness more thoroughly
- Production pushes feel safer and more repeatable
- Container-related checks are covered where useful
- Release workflow is better defined

---

## Scope

### CI Expansion

- Ensure lint, tests, and builds run reliably in CI
- Add deployment-oriented validation where useful
- Add container build validation if it meaningfully improves confidence
- Re-check environment-sensitive scripts in CI context

---

### Release Process

- Create a lightweight release checklist
- Define pre-deploy validation steps
- Define post-deploy smoke-check expectations
- Document rollback/recovery expectations at a practical level

---

### Deployment Confidence

- Verify frontend production build assumptions
- Verify backend production build/start assumptions
- Reconfirm stable behavior after deployment changes
- Reduce surprises during production pushes

---

## Acceptance Criteria

- CI covers build/test/deploy-readiness checks
- Release workflow is documented clearly
- Pre-deploy and post-deploy validation steps are defined
- Container build checks pass if included
- Production push confidence is improved

---

## Deliverables

- updated CI workflows
- release checklist
- deployment verification checklist
- documented smoke-test flow

---

## Notes

- Sprint 4 is about safer shipping, not new product functionality.
- Keep the process lightweight but repeatable.
- The goal is to reduce release risk without adding ceremony for its own sake.
