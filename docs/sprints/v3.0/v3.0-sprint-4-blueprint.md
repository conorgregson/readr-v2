# Sprint 4 Blueprint — CI/CD & Release Confidence

Readr v3.0

**Objective:** Improve release safety by validating deployment readiness earlier and making pushes to production more predictable.

---

## Sprint 4 Goal

- CI validates deploy readiness more thoroughly
- Production pushes feel safer and more repeatable
- Container-related checks are covered where useful
- Release workflow is better defined

---

## Scope

### CI Expansion

- Ensure lint, tests, and builds run reliably in CI
- Add deployment-oriented validation where useful
- Add container build validation if it meaningfully improves confidence
- Re-check environment-sensitive scripts in CI context

### Release Process

- Create a lightweight release checklist
- Define pre-deploy validation steps
- Define post-deploy smoke-check expectations
- Document rollback/recovery expectations at a practical level

### Deployment Confidence

- Verify frontend production build assumptions
- Verify backend production build/start assumptions
- Reconfirm stable behavior after deployment changes
- Reduce surprises during production pushes

---

## Acceptance Criteria

- CI covers build/test/deploy-readiness checks
- Release workflow is documented clearly
- Pre-deploy and post-deploy validation steps are defined
- Container build checks pass if included
- Production push confidence is improved

---

## Deliverables

- updated CI workflows
- release checklist

---

## Recommended Sprint 4 Implementation Focus

Sprint 4 should convert the deployment hardening work from earlier v3.0 sprints into repeatable release confidence. In the broader v3.0 roadmap, Sprint 4 follows deployment audit/environment hardening, Docker/local standardization, and runtime visibility work, so this sprint should focus on enforcing those gains through CI and a lightweight release process rather than introducing new infrastructure or product functionality.

That means the sprint should primarily answer these questions:

- Does CI prove the app is actually deployable, not just locally runnable?
- Can production build/start assumptions be verified before pushing?
- Is there a short, repeatable release flow that reduces human error?
- Are post-deploy smoke checks clearly defined and easy to run?

---

## Implementation Plan

### CI Workflow Hardening

- Review current CI coverage for client and server
- Ensure lint, test, and build steps run consistently in CI
- Add production-oriented validation where it improves release confidence
- Validate backend built-artifact startup, not just TypeScript compilation
- Validate client production build assumptions
- Add container build checks if they provide meaningful deploy-readiness coverage

### Release Safety

- Create a lightweight release checklist for pre-deploy, deploy, and post-deploy steps
- Define which checks must pass before production push
- Define the minimum smoke-test flow required after deployment
- Add practical rollback/recovery guidance for failed deploys or broken post-deploy validation

### Deploy-Readiness Validation

- Reconfirm frontend production build remains stable
- Reconfirm backend production build and runtime entrypoint remain stable
- Re-check environment-sensitive scripts in CI context
- Reduce release surprises caused by missing env assumptions, build/start differences, or container drift

## Suggested Smoke-Test Flow

This sprint should document a short post-deploy smoke-test flow that is fast enough to actually use on every release.

### Minimum Recommended Smoke Checks

- deployed frontend loads successfully
- hosted `/health` responds successfully
- login works against deployed backend
- logout works correctly
- authenticated API requests succeed from deployed frontend
- no obvious console or network errors appear during core flow

### Optional Expanded Smoke Checks

- registration works in production if changed recently
- a representative protected route loads correctly
- key environment-driven behavior still resolves correctly
- container-backed local validation still behaves as expected after release-related changes

## Release Checklist Structure

Sprint 4 should produce a release checklist that covers three stages:

### Pre-Deploy

- pull latest main
- confirm local branch is current
- confirm CI passes
- run final local validation as needed
- confirm environment examples and release notes are up to date
- confirm deploy-target assumptions have not changed unexpectedly

### Deploy

- deploy frontend
- deploy backend
- monitor deployment output for obvious failures
- confirm health route becomes healthy

### Post-Deploy

- run documented smoke checks
- verify frontend/backend communication in production
- verify auth flow still works
- verify no new obvious runtime or console failures
- record verification results for sprint/release notes

### Recovery / Rollback

- redeploy last known good version if needed
- revert the breaking merge/commit if needed
- re-run health and smoke checks after rollback
- document the failure cause and fix before retrying deployment

## Why This Sprint Matters

Sprint 4 is where v3.0 shifts from “deployment hardening exists” to “deployment hardening is consistently enforced.” Earlier v3.0 work establishes environment clarity, Docker-backed local consistency, and runtime visibility; this sprint makes those improvements safer to ship by pushing more validation earlier into CI and by removing ambiguity from the release flow.

---

## Notes

- Sprint 4 is about safer shipping, not new product functionality.
- Keep the process lightweight but repeatable.
- The goal is to reduce release risk without adding ceremony for its own sake.
- The biggest Sprint 4 win is that CI now proves backend startup and authenticated API behavior against a real database-backed test setup, rather than only validating client-side code.
